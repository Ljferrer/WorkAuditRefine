# /war-room — configure a WAR run

You produce a **run config** for `/war` and nothing else: you write `.claude/war/config.json`, then stop. You never decompose a plan, spawn agents, or launch `/war`. The schema, defaults, presets, and validator are owned by [`../war/assets/war-config.mjs`](../war/assets/war-config.mjs) — that script is the source of truth; shell out to it, don't reinvent the schema. Full field reference: [`../war/references/schemas.md`](../war/references/schemas.md) (§ Run config).

## Flow
1. **Pick a starting point.** If `.claude/war/config.json` already exists, show it and offer to start from it. Otherwise present the three presets and ask which to start from:
   - **balanced** — default profile: opus workers at session (`default`) effort, sonnet auditors on `max`, sonnet refiner on `high`, sonnet servitor on `xhigh`, a fable **fix-worker** on `low` (fix rounds + `--ace`) and opus **red-team** sub-agents on `high`. Roster pool: five seats (`correctness`, `cascading-impact`, `plan-faithfulness`, `simplicity`, `performance`) at `deep`, seeded per task by `rosterPolicy: auto` — the Lead composes 1–5 seats per task from the lens catalog, each with an explicit per-seat depth and a one-line rationale (leaf tasks get one `neighbors` seat); `run.ace` on.
   - **thorough** — fable workers on `max`, opus auditors on `max`, sonnet refiner on `xhigh`, opus servitor, an opus **docs-tier worker** on `high` (all-`*.md` tasks), a fable **fix-worker** on `max` and fable **red-team** on `xhigh`. Five-lens pool (`correctness`, `cascading-impact`, `plan-faithfulness`, `security`, `test-fidelity`) under `rosterPolicy: auto` — the Lead composes 1–5 seats per task from the catalog, each at its own depth with a one-line rationale; `run.ace` on.
   - **economy** — single seat, roundLimit 2, ace on: sonnet workers/auditors/refiner/servitor at session effort, a single auditor per task (`rosterPolicy: solo`) widening toward its own pinned four-lens pool (`correctness`, `cascading-impact`, `plan-faithfulness`, `security`), `roundLimit: 2`, `redteamRoundLimit: 2`, `run.ace` inherited on, a haiku **docs-tier worker** on `high` (all-`*.md` tasks), an opus **fix-worker** at session effort (fix rounds and `--ace`) and sonnet **red-team** on `max`. Use for cost-sensitive runs.
   Render the concrete JSON so the user sees exactly what they start from: `node ${CLAUDE_PLUGIN_ROOT}/skills/war/assets/war-config.mjs --preset <name>`.
2. **Offer overrides.** Ask "anything to change?" and grill **only** the dimensions the user names, one at a time. Allowed values (reject anything else — the validator will too):
   - `agents.<role>.model` ∈ `opus | sonnet | haiku | fable`. Roles: `worker` (the base tier — fix rounds and `--ace` inherit it unless split via `agents.worker.fix`, and docs-only tasks use `agents.worker.docs`; see **worker tiers** below), `auditor`, `refiner`, `servitor`.
   - `agents.<role>.effort` ∈ `default | low | medium | high | xhigh | max`. Translate words: "ultrathink" → `max`, "think hard/harder" → `high`/`xhigh`, "normal"/"leave it" → `default`.
   - **Worker tiers** — refine which model runs which worker dispatch (same `model`/`effort` vocabulary; neither is a phase role):
     - `agents.worker.docs` (default `{ model: opus, effort: default }`; thorough → opus/`high`, economy → haiku/`high`) — the tier for **docs-only tasks**. The predicate is mechanical: a task is docs-tier **iff every `Files:` entry matches `*.md`**, evaluated against the **plan's file list, not the diff**. One non-`.md` file in the task → it falls back to the base worker tier.
     - `agents.worker.fix` (**preset-populated** — balanced `fable`/`low`, thorough `fable`/`max`, economy `opus`/`default`) — the tier for **fix rounds and `--ace`** dispatches, so follow-up work can run on a different (usually faster/cheaper) model than the first pass. Override it like any other tier; a hand-written config that drops the block simply lets fix-round and ace workers inherit the base worker.
   - `agents.redteam.model` / `agents.redteam.effort` (same value vocabulary) — the model/effort read **fail-open by `/red-team`** for its probe and adversarial-confirm sub-agents. Not a phase role, but **every preset sets it** (balanced `opus`/`high`, thorough `fable`/`xhigh`, economy `sonnet`/`max`) so it is never blank; override it for the model you want `/red-team` to run against this repo. Only a *missing* config file makes `/red-team` fall back to the session.
   - `agents.snipe.model` / `agents.snipe.effort` (same value vocabulary) — the tier `/snipe` spawns its one-shot audit seats at (#1920). Not a phase role; defaulted `opus`/`high`, explicit `null` = unset (falls back to the auditor tier). Override it for cheaper or heavier quick audits.
   - `audit.roster` — an array of 1–5 seat objects `{ lens, depth? }` (lenses distinct; `depth` ∈ `neighbors | deep`, omitted → `deep`). Present it as a **seat list** — one lens + depth per seat. `audit.rosterPolicy` ∈ `auto | all | solo`; `audit.autoEscalate` (bool). Legacy `covenSize`/`lenses`/`covenPolicy` keys fail validation (removed/renamed) — never write them.
   - `run.maxParallel` — the per-run agent ceiling (the pacing knob for rate-limited accounts). In the /war engine, one global counting semaphore caps agent dispatches in flight across the whole run at that many: workers, auditors, aces, fix workers and gate-audit seats share the one counter, so a wave of N tasks each running its own audit roster still holds at most N sub-agents at once. `/red-team` reads the same knob fail-open and applies it to the probe groups in its own scratch scaffold — that group slicing is a separate, ratified non-goal, outside this ceiling. **Default: leave it absent** — absent means today's unthrottled dispatch and no preset sets it; only pin a value when the operator names this dimension. Shape and validation live in `war-config.mjs` `validate()` — never restate them here.
   - `run.roundLimit` (integer ≥ 1); `run.absorbRounds` (integer ≥ 1 (default 6) — the per-task absorb budget, the ace ladder's own round meter, separate from `run.roundLimit`); `run.afk` (bool); `run.ace` (bool — the per-task ace ladder: pre-merge auto-fix of auditor-flagged nits; default `true`); `run.redteamRoundLimit` (integer ≥ 1; default `3`, the economy preset pins `2`) — `/red-team`'s cumulative grill-round budget, read fail-open by `/red-team`, never the phase engine; at the limit with an unadjudicated root finding open — or from round 2 with an unadjudicated needs-decision finding — the gate routes the plan back upstream (never while coverage is incomplete).
   - `overrides.gate` / `workingBranch` / `landingBranch` / `learningsTarget` / `testPattern` — `null` lets `/war` auto-detect; a string pins it. `testPattern` is the **test-floor glob set** (space-separated single-star tokens, e.g. `'*.test.ts *.test.tsx'`): `null` = today's floor defaults (`/war` proposes one from the target's test conventions at Setup, pinned **together with the gate** — floor ⊆ gate — though under `--afk` that confirmation is not the final word on the *value*: a proposal the sanity floor rejects stays **pending** and is re-checked at each phase launch, adopted monotonically once every token matches and the value re-passes the validator's `overrides.testPattern` check); a string pins the target's glob set. Its **glob-safe charset is enforced by the validator** — quotes, `;`, backticks, `$`, and newlines are rejected (the value is embedded into an agent-executed shell command).
   - `overrides.ghUser` — the personal `gh` account `/war` asserts is active before every gh write batch (via `gh-preflight.sh`), for multi-account machines; `null` (default) skips the check. It stays in the **local** `.claude/war/config.json` and ships `null` — never commit a real handle.
   - `memory.topK` (integer ≥ 1, default `10`) — max prior-lesson blocks the Lead prefetches per seat. `memory.retrieval` (bool, default `true`) — set `false` to skip the prefetch entirely. (`memory.commitLearnings` is **not** an override here — it is the standing opt-in ask in step 3.)
   - `hooks.replyStandard` (bool, default `true`; `null` = unset, the default applies) — toggles the plugin's Reply Standard hook family under `hooks/reply-standard/`: the `UserPromptSubmit` card + `Stop` meter, and the WAR-seat pair — a `SubagentStart` seat-edition card + `SubagentStop` meter (matched to `work-audit-refine:war-*` agent types, rows to `subagent-meter.log`). Read fail-open by the hooks' own gate wrapper in the project the session runs in, never by the phase engine; only an explicit `false` disables.
   - `hooks.valeMarkdown` (bool, default `true`; `null` = unset, the default applies) — toggles the plugin's advisory Vale Markdown lint (`PostToolUse` on `Edit`/`Write`, `.md` files only, under `hooks/vale-md/`). Self-gated fail-open by the hook script itself, never by the phase engine; advisory only, and a machine without the `vale` binary silently no-ops; only an explicit `false` disables.
   - `hooks.valeStyle` (enum, default `workAuditRefine`; `null` = unset, the default applies) — vale-md profile selector: `house | workAuditRefine | google | microsoftFork | writeGood | proselint | alex | readability | redhat | custom`. `workAuditRefine` is the repo's tuned fork (house rules + a tuned Google cut); `google` is raw upstream Google. Every named style is vendored in the plugin (`hooks/vale-md/styles/`, no network); `custom` reads the project-side `.claude/war/vale/.vale.ini` and fail-opens to the default when that file is absent. Subordinate to `hooks.valeMarkdown` — when that is `false`, nothing runs. When the operator picks `custom`, read [references/vale-custom-interview.md](references/vale-custom-interview.md) and run that interview — its first act is a non-blocking repo pattern-mining subagent, then the grill, then the project-side profile write.
   When the user touches roster settings, read the canonical `audit.autoEscalate` row in [`../war/references/schemas.md`](../war/references/schemas.md) (§ Run config) — **`rosterPolicy: "solo"` alone does not pin one auditor**; that row gives the widen semantics and the `autoEscalate: false` pin.
3. **Ask the learnings-publication opt-in** — a **standing ask every run** (not an override the operator must name). Publication is **off by default**: distilled lessons stay in the local, untracked memory root unless the operator opts in here. Surface the value pitch, then record the answer:
   > Commit distilled, lint-scrubbed engineering lessons under `docs/learnings/` so they travel with the repo and compound across your team? Each rides its phase PR and is human-reviewed like code.
   Yes → set `memory.commitLearnings: true`. No or silence → leave it `false` (the default). Either way the fail-closed redaction lint guards what publishes, and local-root lessons are always captured regardless.
4. **Resolve provisioning** (`run.provision` — the commands that make a fresh worker worktree gate-ready). Ask the module what to do rather than deciding yourself — pass the assembled-so-far config to `resolveProvision` (exported by `war-config.mjs`); it returns `{ provision, source, scout }`:
   - **`scout: false` with a non-empty `provision`** — the operator pinned an explicit list (or it was carried from an existing config). Honor it **verbatim**; do **not** run the scout. Leave `run.provision` and `run.provisionSource` exactly as they are.
   - **`scout: false` with an empty `provision`** — `provisionAuto` is off. Leave `run.provision: []` / `run.provisionSource: "none"`; no scout, no steps.
   - **`scout: true`** — `provisionAuto` is on and no explicit list exists. Run the read-only setup-scout (`agents/war-setup-scout.md`) against the target repo via `Agent`. Present its **proposed `provision` list + `source` + `rationale`** to the operator and ask them to confirm or edit. Write the **CONFIRMED** list into `run.provision` and the scout's `source` into `run.provisionSource`. If the operator declines all steps, write `run.provision: []` / `run.provisionSource: "none"`.
   - **`--refresh-provision`** — when invoked with this flag, first **clear** any existing `run.provision` (set it to `[]` and `run.provisionSource: "none"`) so `resolveProvision` reports `scout: true`, then re-scout as above. This is the only way to re-derive a list that is already pinned (a non-empty list otherwise short-circuits the scout).
5. **Submodule overlap check.** Before showing the final config, inspect the plan file (if provided) for task target paths. If any plan target path overlaps with a `.gitmodules` submodule path in the repo (i.e. any target is under a declared submodule prefix), surface a **setup warning** for each overlap before proceeding:
   > ⚠ task `<task-id>` targets `<path>` inside submodule `<submodule-path>`; expect `/war`'s submodule router to propose a submodule task + paired gitlink-bump task for your approval at Decompose — see [`../war/references/submodule-flows.md`](../war/references/submodule-flows.md) (§ Submodule router). An undeclared submodule touch is still refused at merge.
   If no `.gitmodules` exists, or no overlaps are found, continue silently. This warning does not block config writing — it is informational so the operator can decide before investing a full run.
6. **Show the assembled config** as pretty JSON and ask for explicit confirmation.
7. **Validate, then write.** Validate through the module and only write on success (write to a temp file first so a failure never truncates an existing config):
   ```bash
   mkdir -p .claude/war
   printf '%s' '<assembled-json>' \
     | node ${CLAUDE_PLUGIN_ROOT}/skills/war/assets/war-config.mjs --stdin --fill-defaults \
     > .claude/war/config.json.tmp \
     && mv .claude/war/config.json.tmp .claude/war/config.json \
     || { echo "validation failed — config NOT written"; rm -f .claude/war/config.json.tmp; }
   ```
   If it failed, show the validator's errors, fix them with the user, and retry. Never write an invalid or unvalidated file. (`--fill-defaults` writes the complete resolved config, so the file is self-describing.)
8. **Stop.** Tell the user: *"Config written to `.claude/war/config.json` (profile: <profile>). Run `/war <plan>` to use it, or `/war <plan> --config <path>` to point at a different file."* Do not launch `/war`.

## Notes
- Conversation-only: no `Workflow`, no git writes beyond the single config file. The **only** `Agent` you may spawn is the read-only setup-scout (step 4), and only when `resolveProvision` reports `scout: true` (or `--refresh-provision` was passed); it is `Read/Grep/Glob`-only and changes nothing.
- If a `[Fact-Forcing Gate]` (GateGuard) blocks the write, present the facts it lists, then retry the identical command.
