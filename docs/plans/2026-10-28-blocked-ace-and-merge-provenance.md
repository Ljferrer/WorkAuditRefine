## Context — the gap / problem

Five Aligned tasks across three runs escalated `pin-transfer:unverified` after an ace worker committed and pushed a new commit, then returned `status: blocked` (verified: RCA §Bug 1 at `889f2cfc`). The engine's four ace arms (`aceWhy`, `swWhy`, `rwWhy`, `twWhy` in `workflow-template.js`) treat a blocked result as "no commit", so the new commit is neither reverted nor audited (verified: `workflow-template.js` at `889f2cfc`). At the merge slot `verifyPinTransfer` found `approved_tree !== content_tree`, retried `roundLimit` times on that deterministic fact, and escalated with the note "pin transfer has no independent Git proof of the approved content and reported destination" (verified: RCA timeline table, 26 of 26 Aligned and WAR attempts failed only that clause; the 6 AutoIndex attempts show the same signature per the RCA critic, single-sourced). The same signature holds task 2.4 in #2412 and an unfiled AutoIndex task (verified: RCA §Bug 1). The terminal pass arm treats blocked the same way (verified: `twWhy` at `889f2cfc`): a blocked terminal ace that committed is logged as "no terminal commit", its rows carry or demote, and the polish-branch merge runs only in the non-blocked arm, so the commit is orphaned on the polish branch and never judged or merged (verified: the `twWhy` arm and the `merge:p<N>-terminal` dispatch site at `889f2cfc`).

The five blocked workers each cited the trailer layout: the ace prompts demand the `Ace-Charge` trailer "as its OWN final paragraph" while the harness asks every agent to end commits with an attribution line (verified: RCA §Bug 1, the journal `blocked_reason` texts), and git parses trailers only from the last paragraph (verified: TRIAL-2 at `889f2cfc`). Seven workers with the same layout returned `implemented` and merged, so the layout explains the commits, and the engine arm explains the holds (verified: RCA §Bug 1). The only repair after push is a force push the worker card forbids (verified: RCA §Bug 1 step 6; issue #2380 (2026-10-17) row 3).

The sanctioned recovery relaunch proved none of nine merged tasks, because `task-integrated.sh` reads a git-parsed `WAR-Task` trailer on worker commits, and those trailers sat in a non-final paragraph, were absent from ace commits, or the tip was an engine revert with no trailer (verified: `task-integrated-replay.txt` at `889f2cfc`). That produced the `empty-unmatched` holds and the dep-failed cascade (verified: RCA §Downstream consequences).

The stale-install gate failure had three sites: the pin-transfer rebase before the merge-task gate, a dep-wave worker's first-act rebase before its own gate, and the `_refinery` base re-run, which has no install at all (verified: RCA §Downstream consequences, one reader, not cross-verified; the two sites beyond the recovery run are the normal-run instances the RCA names).

Plan 1 of the 2026-09-06 campaign landed in full on 2026-09-10 (verified: PR #2297 via `gh`, epics #2107, #2108, #2114 closed). No branch exists for plans 2 or 3 of that campaign (verified: `git ls-remote` at interview time). The five unjudged Aligned commits are already on Aligned master through an operator override (verified: RCA §Downstream consequences).

## Pivotal constraints

- The `verifyPinTransfer` tree clause is the only guard against merging an unjudged commit. It is never relaxed (user) Q2, PIN-25 ‡. The issue's "Expected" bullet 1 is not implemented.
- The ace path never turns a mergeable task into a hold (ADR 0013, ADR 0012). The one residual, a dead or unusable probe or a non-descendant tip, is a named backstop row.
- No change to `HARD_ESCALATION_REASONS` or `KNOWN_LAND_DECISIONS`. The pin reason stays `escalate` (ADR 0049 PIN-6, ADR 0005).
- `MergeResult.status` is not widened. A failed provision step rides an optional `provision` sub-object in the env-outcome shape (ADR 0021).
- A task branch whose tip is an ancestor of the integration tip is never rebased, moved or re-merged (user) Q3, marked ‡.
- This plan's own `/war` run executes from the installed marketplace plugin, version 0.21.19, on today's fast-forward engine (user) Q9. A recovery relaunch executes from the same plugin root and version as the launch it recovers. This run executes the installed 0.21.19 Lead, which stamps no such field, so the Lead posts the root and version in each phase report; later runs read them from the manifest fields Task 5.1 adds.
- The docs PR that carries the RCA and this plan merges with a merge commit, never a squash, so `889f2cfc` stays reachable for the trial rows.
- `/red-team`'s `ff-topology` probe encodes fast-forward task merges as truth. This plan retires that premise, so the expected verdict is ADJUDICATED (ADR 0043), and Task 5.3 updates the lens family.
- ADR 0040 does not interact with the provision floor: a missing module reproduces on a fresh-TMPDIR re-run, so it is never environment-class, and a re-provision step inside the merge body is not a recovery dispatch.
- Polish and terminal merges stay fast-forward and are never proven by the helper.
- Byte budgets at `889f2cfc` (verified: `prompt-surface-budgets.test.mjs`, which budgets all four surfaces): `agents/war-worker.md` 208 B of headroom, `agents/war-refiner.md` 103 B, `skills/war/SKILL.md` 98 B, `CONTEXT.md` 720 B. New glossary bodies go born-cold into `glossary-cold.md` behind pointer lines, and the manifest field list is de-mirrored from `skills/war/SKILL.md` to `run-manifest.md`. New card doctrine lands in `references/` behind a trigger pointer (ADR 0042), and the card and the dispatched prompt change in one commit.

## Commander's Intent

- **Purpose:** a WAR run never holds an approved task because an ace worker committed after approval, except for two named residuals (a tip that does not descend from the pre-dispatch tip, and a revert dispatch that itself dies); never merges a commit no panel judged; proves every task merged through a merge commit under this engine on a sanctioned recovery; and never runs a refiner or dep-wave gate on a tree its provision steps have not seen.
- **Method:** read the task branch tip through a refiner probe after every ace result, and judge or revert any post-approval commit through the existing ace re-audit seam. At the merge slot, stop retrying a deterministic tree mismatch and name the cause. Merge each task with a `--no-ff` merge commit that carries `WAR-Task`, and prove ownership from that merge commit. Keep the tree check. Re-run provision before any gate on a tree that changed. Retire the fast-forward premise in doctrine and in the red-team lens.
- **Mechanism latitude:** the probe's dispatch kind, label, and whether it folds into the ace-gate result, as long as it fires on every ace result arm; how the ancestry, tree and existing-merge tests are written, with acceptance only through the predicate; a lockfile narrowing of the re-provision trigger as an optimization over the floor; the representation of the typed pin reason; fixture shapes and names; the grep guard's layout; which `references/` file hosts the evicted card sentence and the pointer wording; the merge-commit subject line; where the `provision_tree` preamble line sits after `tip_sha`.
